# ✅ TechNote v1.0 릴리스 체크리스트

> **작성일**: 2026-08-23
> **목적**: "품질이 충분히 좋아지면 끝낸다"는 **판정 불가능한 종료 조건**을 버리고,

## 왜 이 문서가 필요한가 (근거)

3.5개월(2026-05-13 ~ 08-16), 215 커밋. [PRD.md](./PRD.md)의 기능 요구사항 **F-01~F-12가 전부 완료**,
작업 보드는 15개 중 14개 완료. 그런데도 끝나지 않는 이유는 제품이 미완이라서가 아니라,
**끝났다고 판정할 기준이 없어서**다. 두 가지가 겹쳐 있다.

**1. eval 이 이미 해상도를 다 썼다.** `backend/evals/results/` 전 회차(n=48, 20문항 고정 실행분) 집계:

| 기간 | 실행 수 | 평균 통과율 | 표준편차 | 범위 |
|---|---|---|---|---|
| 7월 | 25회 | 65.6% | ±14.0%p | 30 ~ 90% |
| 8월 | 23회 | 72.0% | ±16.7%p | 15 ~ 90% |

20문항이면 **1문항 = 5%p** 인데 실행 간 편동이 ±15%p다. 즉 **4문항 미만의 개선은 원리적으로
관측 불가능**하다. 게다가 일일 루틴은 `--generate 20`으로 **매번 다른 질문을 새로 합성**하므로,
여기에 문항 자체의 분산까지 더해진다. 개별 커밋이 눈금 안쪽에서 움직이니 아무리 고쳐도
"좋아졌다"는 확신이 오지 않는 게 당연하다.

**2. 현실 기준이 없다.** 실사용자가 본인 계정 하나뿐이다. 유일한 품질 기준이 본인이 만든
문항 생성기인데, 자기가 낸 문제로 자기를 채점하는 루프에는 종료 조건이 생길 수 없다.

→ 그래서 **품질을 더 올려서 끝내는 대신, 끝난 걸로 선언하고 판단을 외부(실사용자)로 넘긴다.**

### 1-2. GCP 콘솔 — Cloud Tasks (선택, 미루면 그대로 동작함)

**이게 무슨 작업인가.** 파일을 업로드하면 목차 추출 + Vision 분류가 도는데, 이게 수십 초
걸려서 업로드 응답과 분리돼 백그라운드로 실행된다. 그 백그라운드를 **누가 붙들고 있느냐**가
설정 유무의 차이다.

| | 지금 (미설정) | Cloud Tasks 설정 후 |
|---|---|---|
| 실행 주체 | Cloud Run 인스턴스 안의 `asyncio.create_task` | Cloud Tasks 큐가 `/internal/analyze` 를 HTTP 로 호출 |
| 인스턴스가 회수되면 | **분석이 조용히 중단됨** | 큐가 최대 3회 재시도 |
| 실패 시 사용자에게 보이는 것 | 문서가 `analyzing` 상태로 영영 멈춤 | 재시도 후에도 실패하면 `error` 로 표시 |

핵심 위험은 하나다. Cloud Run 은 **HTTP 응답이 끝나면 인스턴스 CPU 를 스로틀하거나 인스턴스를
회수**할 수 있다. 업로드 응답은 이미 나갔는데 분석은 아직 도는 중이므로, 큰 PDF 일수록
중간에 잘릴 수 있다. 이때는 예외 처리도 못 타서 `status: "error"` 조차 안 찍히고
**문서가 `analyzing` 에 갇힌다.**

**지금 미뤄도 되나.** 된다. 코드는 이미 폴백으로 잘 돌고 있고 지금까지 문서 수십 개를
그렇게 처리했다. **혼자 쓰는 동안에는 문제가 드러나지 않는다** — 업로드가 한 번에 하나씩,
인스턴스가 살아 있는 동안 끝나기 때문이다.

**언제 필요해지나.** 3단계에서 실사용자가 붙고 **여러 명이 동시에 큰 PDF 를 올리기 시작할 때**다.
그 시점에 "업로드했는데 분석이 안 끝나요" 신고가 들어오면 이 설정이 답이다.

> **판단**: v1.0 출시를 막는 항목은 아니다. 아래 명령은 필요해질 때 그대로 실행하면 된다.
> 이 항목이 미완인 상태로 v1.0 을 내보내도 무방하다.

- [ ] Cloud Tasks API 활성화
  ```bash
  gcloud services enable cloudtasks.googleapis.com
  ```
- [ ] 분석 큐 생성
  ```bash
  gcloud tasks queues create vision-rag-analysis --location=asia-northeast3 --max-concurrent-dispatches=5 --max-attempts=3
  ```
- [ ] Cloud Build 트리거 변수 3종 추가 (GCP 콘솔 → Cloud Build → 트리거 → 편집)
  - `_CLOUD_TASKS_QUEUE` = `projects/{project_id}/locations/asia-northeast3/queues/vision-rag-analysis`
  - `_CLOUD_RUN_URL` = Cloud Run 서비스 URL
  - `_INTERNAL_TASK_SECRET` = `openssl rand -hex 32` 결과
    - ⚠️ 이 셋은 **한 묶음**이다. `_CLOUD_TASKS_QUEUE` 를 넣었는데 `_INTERNAL_TASK_SECRET` 이
      비어 있으면 프로덕션 부팅이 차단된다(`main.py` fail-closed 가드). 셋 다 넣거나, 셋 다 비우거나.

## 3단계 — 실사용자 3~5명

여기서부터 백로그의 우선순위는 내가 아니라 **사용자가 정한다.** 실제 불만은 항상 예상과
다르고, 무엇보다 **개수가 유한하다.**

- [ ] **대상 선정 3~5명** — 실제로 매뉴얼을 뒤지는 사람(현장 엔지니어/정비). 개발자 친구는 이 목적에 맞지 않는다
- [ ] **각자의 매뉴얼을 직접 올리게 한다.** 내가 올린 문서로 테스트하면 "내 문서에서 잘 되는 시스템"을 확인할 뿐이다
- [ ] **첫 주에 딱 하나만 묻는다**: "찾던 걸 찾았나요? 못 찾았으면 뭘 물어봤나요?"
      만족도 점수 대신 **실패한 질문 원문**을 모은다 — 그게 다음 골든셋이 된다
- [ ] 수집한 실패 질문을 `backend/evals/dataset.yaml` 에 추가 (여기서 데이터셋이 100문항으로 자란다)
- [ ] 유저 피드백 UI(답변 좋아요/싫어요)는 **사용자가 실제로 불편을 호소한 뒤에** 만든다 → [v2_backlog.md](./v2_backlog.md)

### 종료 조건 (이 문서의 목적)

**1·2단계 체크박스가 전부 채워지면 v1.0은 끝난 것이다.** 3단계에서 올라온 실사용자
피드백만이 다음 작업의 입력이 된다. eval 점수는 더 이상 작업 지시가 아니라 회귀 알람이다.
