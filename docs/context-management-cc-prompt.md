# 클로드 코드용 프롬프트 — 컨텍스트 관리 전면 재점검

아래 블록을 그대로 복사해서 클로드 코드에 붙여넣으세요.

---

```
@docs/context-management-benchmark.md 를 읽어라.

이 문서는 다른 세션에서 작성된 컨텍스트 관리 벤치마킹 분석이다.
**문서 내용을 사실로 신뢰하지 말고**, 이 저장소 코드를 직접 읽어서 처음부터 독립적으로 재점검해라.

## 1단계 — 현황 재감사 (코드 직접 확인)

문서를 참고만 하되, 다음을 네가 직접 조사해서 근거(file:line)와 함께 보고해라.

- 프롬프트가 조립되는 모든 지점: `backend/app/prompts.py`, `services/agent_service.py`,
  `services/agentic_graph.py`, `services/agentic/` 전체
- `chat_history`가 만들어지고 잘리고 프롬프트에 주입되는 **모든** 경로
  (`routers/chat.py` → 파이프라인 → 각 LLM 호출까지 끝까지 추적)
- 프론트엔드에서 히스토리가 전송되는 방식: `frontend/src/hooks/useChatStream.ts`,
  `store/useChatStore.ts`, 관련 타입 정의
- 대화 저장 스키마: `services/conversation_service.py`
- Gemini 호출부의 파트 순서 / 캐싱 관련 옵션 사용 여부
- ToC 데이터 구조와 실제 활용 범위: `services/agentic/toc.py`, `services/metadata_service.py`

## 2단계 — 문서 주장 검증

문서 1장(현재 상태 진단)의 8개 항목, 2장의 기법 A~G, 3장의 우선순위 표를 각각
`[확인됨]` / `[부정확 — 실제로는 …]` / `[이미 해결됨]` 으로 판정하고 근거 라인을 달아라.
문서가 놓친 컨텍스트 관리 문제가 있으면 `[추가 발견]` 으로 별도 정리해라.

특히 아래는 반드시 실측으로 확인해라(추측 금지):
- `text_fallback_prompt` / Vision 호출에서 대용량 콘텐츠가 가변 요소보다 뒤에 오는지
- 히스토리 절단 로직이 정말 3곳에 중복인지, 각각 파라미터가 다른지
- 프론트가 보내는 히스토리와 백엔드가 실제 사용하는 양의 차이
- 현재 `usage_metadata` / 토큰 사용량이 로깅되고 있는지

## 3단계 — 교정된 실행 계획

검증 결과를 반영해서 우선순위를 다시 매겨라. 문서의 순위를 그대로 따르지 말고,
**이 코드베이스 실제 상태 기준**으로 "효과 / 난이도 / 리스크"를 재산정해라.
각 항목마다 변경할 파일과 함수를 명시하고, 되돌리기 쉬운 단위로 커밋을 쪼개라.

## 4단계 — 승인 후 구현

계획을 먼저 보여주고 내 승인을 받아라. 승인 전에는 코드를 수정하지 마라.
승인 후 구현할 때는:
- 단계마다 `cd backend && source venv/bin/activate && pytest` 통과 확인
- 컨텍스트 조립 로직을 바꿨다면 `python -m evals.run_eval --local` 을 변경 전/후로 실행해
  routing/document/page 정확도와 토큰 사용량을 비교해서 보고
- 프롬프트 문자열은 `app/prompts.py` 밖에 인라인하지 마라 (CLAUDE.md 규칙)
- 멀티턴 회귀를 잡기 위해, 지시대명사 후속 질문("그럼 그 알람은?") 골든 케이스를
  eval 데이터셋에 추가할지 제안해라

## 제약

- 한 번에 전부 고치려 하지 말고, 검증 → 계획 → 승인 → 단계별 구현 순서를 지켜라
- 확신이 없는 부분은 추측하지 말고 "확인 필요"로 남겨라
- 기존 API 계약을 깨는 변경은 하위 호환 경로를 함께 제시해라
```
