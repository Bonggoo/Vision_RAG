## 요약

사전 조사 문서의 진단을 코드로 재감사하고 토큰 사용량을 실측한 뒤, 근거가 확인된
항목만 적용했다. **가장 큰 성과는 사전 조사가 다루지 않은 Phase 2 프롬프트 순서**였다.

| 단계 | 입력 토큰 | 캐시 적중 (전) | 캐시 적중 (후) |
|---|---:|---:|---:|
| **Phase 2 본문 정밀탐색** | 38,963 | **0%** | **95%** |
| Phase 1-2 페이지선택 | 32,261 | 89% | 89% (유지) |
| Phase 1 문서선택 | 6,856 | 59% | 59% |
| Phase 3 Vision 답변 | 1,247 | 0% | 0% (아래 참고) |

Phase 2 는 파이프라인 최대 입력인데 질문이 본문보다 앞에 있어 전량이 캐시 대상에서
빠져 있었다. 순서를 뒤집어 같은 섹션에 후속 질문이 이어질 때 **36,835 토큰이 할인**된다.

측정 방법: `app/utils/llm_usage.py` 가 남기는 `🧮 [Usage]` 로그.
`langchain_google_genai` 4.2.2 의 `usage_metadata.input_token_details.cache_read` 기준.

|---|---|---|
| 1 | 절단 로직이 백엔드 3곳에 중복 | **부정확** — 백엔드는 2곳(`llm_steps.format_chat_context`, `agent_service._do_vision_analysis`). `agentic_graph.py` 의 두 복붙은 `f3c1784` 리팩터에서 이미 통합됨. 세 번째는 백엔드가 아니라 프론트(`useChatStream.ts`) |
| 2 | 문자 수 기준 절단 | 확인됨 |

| 4 | 프론트가 전체 히스토리 전송 | **부정확** — 프론트가 이미 6개 메시지 × 300자로 절단해 보냄(약 1.8KB) |
| 5 | `text_fallback_prompt` 가변 요소가 본문보다 앞 | 확인됨 |
| 6 | Vision 에서 PDF 가 뒤 파트 | 확인됨 |
| 7 | `full_text[:8000]` 고정 절단 | 확인됨 (단 Vision 실패 시에만 타는 폴백 경로라 상시 영향 없음) |
| 8 | 캐싱 미사용 · 계측 없음 | **절반 부정확** — 계측이 없었던 것은 사실이나, 암묵적 캐싱은 이미 동작 중이었음(89%) |

**사전 조사가 놓친 항목**

- `refine_pages_prompt`(Phase 2)의 질문 선행 — 파이프라인 최대 입력, 적중 0%
- `select_document_prompt` 의 ToC 증거가 고정 문서목록 **안에** 섞여 프리픽스를 오염
- `agent_service.py` 에 인라인 프롬프트 7건 (CLAUDE.md 규칙 위반)
- eval 하네스에 멀티턴 케이스가 없어 맥락 관련 변경의 효과를 잴 수 없었음

### 프롬프트 변수 순서 규칙

`prompts.py` 의 해당 함수들에 `⚠️ 변수 순서 주의` 독스트링을 달아 두었다.
**대용량·고정 콘텐츠(ToC / 섹션 본문 / PDF / 문서목록)를 앞에, 가변 요소
(대화 맥락 / 이전 참조 / 질문)를 뒤에** 두어야 한다. 순서를 바꾸면 캐시가 통째로 깨진다.

## 3. 시도했다가 되돌린 것

**`select_pages`(Phase 1-2)에 대화 이력 주입** — 되돌림.

지시대명사 후속 질문("그럼 그 알람은?")이 이 프로젝트의 체감 품질 이슈라는 전제로
계획했으나, 측정 결과 전제가 성립하지 않았다.

- 멀티턴 골든 3건(지시대명사 / 생략형 / 맥락전환 음성 케이스)이 **주입 전에도 전부 통과**.
  기존 `previous_reference` 이어받기 경로가 이미 제 역할을 하고 있었다.
- 별도 probe 에서 타겟 페이지가 넓어지는 부작용 관찰
  (`[700, 701]` → `[700, 806, 846]`). 페이지가 늘면 Vision 입력이 늘어난다.

캐시를 깨지 않는 위치(ToC 뒤)에 넣을 수는 있었으나, 이득이 없는 변경은 남기지 않았다.
**재시도하려면 먼저 실패하는 멀티턴 케이스를 찾아 eval 에 추가할 것.**

## 4. 남은 항목

- **세션 요약(compaction)** — 6턴 초과 시 요약으로 치환. 다만 위 3번 결과를 보면
  현재 맥락 유지가 예상보다 잘 되고 있어, **실패 케이스를 먼저 확보하는 것이 순서**다.
- **서버사이드 히스토리 소유** — 페이로드 이득은 ~1.8KB 로 무의미. 새로고침·멀티탭
  일관성이 목적이라면 가치 있음.
- **Phase 1 문서선택 59% 천장** — ToC 증거를 분리해 구조적 오염은 제거했으나 수치는
  그대로였다. 캐시 블록 경계 때문으로 보이며, 더 올리려면 `_narrow_candidates` 의
  문서 정렬 순서까지 고정해야 한다(후보 순서가 되묻기 메뉴에 영향을 주므로 별도 검토 필요).
- **Vision 캐시** — 현재 미니 PDF 가 1,247 토큰 수준이라 암묵적 캐시 최소 크기에 못 미친다.
  파트 순서는 정렬해 두었으므로 페이지 수가 많은 문서에서는 적중할 수 있다.
- **업로드 경로 인라인 프롬프트 6건** — `agent_service.py` 의 ToC 추출·메타데이터 추출 등.
  이번에는 채팅 경로만 정리했다.

## 5. eval 실행 참고

로컬 파이프라인 직접 호출 시 **GCS 문서를 봐야 하므로** `USE_LOCAL_STORAGE=False` 가 필요하다
(`.env` 기본값이 `True` 라 그대로 돌리면 문서 0건으로 전부 실패한다).

```bash
cd backend && source venv/bin/activate
USE_LOCAL_STORAGE=False python -m evals.run_eval --local
```

멀티턴 케이스는 `history` 와 `previous_reference` 를 **함께** 지정해야 한다.
프론트가 매 턴 둘 다 보내므로, 하나만 주면 실제 UX 와 다른 경로를 검증하게 된다.
